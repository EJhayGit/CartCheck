# CartCheck implementation roadmap

**Status:** Approved planning sequence (2026-09-24). Each milestone should leave a demonstrable slice and pass its gate before the next begins. No implementation has started.

| Milestone | Features and database changes | Expected deliverables | Acceptance gate and tests |
| --- | --- | --- | --- |
| **1. Foundation and Supabase-ready database** | Replace sightings schema with account/session, starter/private product, trip, and trip-item tables. Add constraints for quantity, nullable estimated/actual item totals, PHP/USD/EUR, one active trip, and snapshots. Prepare Render/Supabase configuration without changing a hosted project yet. | Numbered migrations, readable fresh schema, idempotent ~100-item seed, exact money/validation helpers, local setup and placeholder env documentation. | Disposable PostgreSQL initializes twice without duplicate starters; blank and zero differ; no invented starter prices. SQL checks and `node:test` for quantity, amounts, currency. Verify future Supabase connection mode when accounts exist. |
| **2. Accounts and real-API shell** | Express-managed registration, login/logout, sessions, owner-scoped queries, first active trip, secure cookies, rate limits, and same-origin serving path. Depends on milestone 1. | Auth API, React auth gate/forms, production configuration with no mock fallback. | Refresh restores login; logout revokes it; foreign account access fails. Two-account API tests, cookie/Origin checks, client build and local production-mode smoke test. |
| **3. Catalog and quick registration** | Private copies of starter items, search/category filter, custom registration/edit, optional image URL. Depends on accounts/products tables. | Catalog API and screen; simple registration form with prefilled failed search. | Shopper can find a starter and create a custom item without brand, variant, price or unit. Private edits do not affect another account. API isolation/validation tests plus keyboard and no-result checks. |
| **4. Functional grocery list** | Add/set/edit/remove single entries; displayed name, quantity and optional unit label; category search/organization; revision handling. Depends on catalog and trip-item schema. | Cart API and primary checklist UI. | Re-adding a product edits one row using absolute values; a network retry cannot increment quantity. List survives refresh. Domain/API duplicate and revision tests; phone/desktop checklist walkthrough. |
| **5. Purchase progress** | Bought/unbought flag and local hide-checked view. Depends on working list. | Checkbox and hide-checked interactions. | Purchased rows remain available, can be unmarked, and are not deleted when hidden. API persistence and keyboard/visibility checks. |
| **6. Optional prices and budget** | Independent nullable estimated/actual item totals, optional trip budget, known subtotals and missing counts. Depends on list and exact money rules. | Amount/budget API fields and secondary UI controls. | A shopper can add, check, and shop without money fields. Zero is known; null is unknown; incomplete comparisons are labeled; over-budget warnings do not block. Focused domain/API tests and optional-money walkthrough. |
| **7. Finish Trip and history** | Transactional, idempotent finish; bought/not-bought snapshots; fresh empty trip; dated history list/detail; then confirmed past-trip correction. Depends on accounts, list, and amount rules. | Finish review/API, history screens/API, correction review/API. | Unchecked items are not bought and do not roll over; unpriced bought items can finish; duplicate confirm creates one trip; corrections retain date and recompute totals. DB retry/concurrency, snapshot, stale-revision and two-account tests; complete browser trip. |
| **8. Release and course evidence** | Public Render web/API deployment and Supabase PostgreSQL connection, final accessibility/security work and documentation. Depends on all slices. | HTTPS application, updated README/env examples/workflow, screenshots, revised proposal, visual mockup/design-system submission, weekly reports, demo video, security/privacy checklist and AI-use evidence. | Complete checklist-only and optional-budget trips work publicly across sessions; another account stays isolated. Client build, all tests, disposable migration, responsive/keyboard matrix, `/healthz` and `/readyz`, dependency audit and privacy checklist. |

Authentication precedes private catalog and list work; the database schema precedes authentication. Purchase status precedes Finish Trip, and optional amount fields precede complete spending summaries. History correction follows finished-trip read-only history. The Render and Supabase accounts are intended but not yet created; local disposable PostgreSQL provides the early verification gate. Never run the template's destructive sightings seed/reset on retained data.
